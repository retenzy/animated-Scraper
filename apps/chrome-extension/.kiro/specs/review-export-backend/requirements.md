# Requirements Document

## Introduction

A lightweight backend server that receives Amazon product review data from the Chrome extension once extraction is complete. The server accepts a POST request containing the extracted reviews, saves the data as a file (JSON and/or CSV), and makes the saved file immediately available for download. This removes the need for the extension to handle file generation and download entirely client-side, and opens the door to server-side storage or forwarding of review data in the future.

## Glossary

- **Server**: The Node.js/Express backend process that receives and stores review data.
- **Client**: The Chrome extension (popup.js) that sends extracted review data to the Server.
- **Review**: A single Amazon product review object containing fields: `id`, `title`, `rating`, `author`, `date`, `body`, `verified`, `helpful`.
- **Payload**: The JSON body of the POST request sent by the Client, containing metadata and an array of Reviews.
- **Export_File**: A file (JSON or CSV) generated by the Server from the received Payload.
- **Download_Endpoint**: The HTTP GET endpoint that serves a generated Export_File to the requester.
- **ASIN**: Amazon Standard Identification Number — a 10-character alphanumeric product identifier.
- **fileId**: A non-empty string token returned by the Server upon a successful POST, used to construct download URLs.

## Requirements

### Requirement 1: Receive Review Data

**User Story:** As a Chrome extension, I want to POST extracted review data to the backend server, so that the server can persist the data independently of the browser session.

#### Acceptance Criteria

1. WHEN a POST request is received at `/api/reviews`, THE Server SHALL accept a JSON body containing a `reviews` array of at most 500 items and an optional `metadata` object (including `productTitle`, `asin`, `extractedAt`).
2. WHEN the `reviews` array in the request body is empty OR contains more than 500 items, THE Server SHALL return HTTP 400 with a JSON body containing an `error` field with a descriptive message.
3. WHEN the request body is missing or is not parseable as JSON, THE Server SHALL return HTTP 400 with a JSON body containing an `error` field with a descriptive message.
4. WHEN the request body is valid JSON but does not contain a `reviews` key, THE Server SHALL return HTTP 400 with a JSON body containing an `error` field stating that `reviews` is required.
5. WHEN a POST request is received with a non-empty `reviews` array (each item containing at least a non-empty `reviewText` string) and the array does not exceed 500 items, THE Server SHALL respond with HTTP 200 and a JSON body containing a non-empty `fileId` string that can be used to download the generated Export_File.
6. THE Server SHALL accept CORS requests from `chrome-extension://*` origins so that the Client can call the endpoint directly from the extension.

### Requirement 2: Save Reviews as Files

**User Story:** As a user, I want the backend to save extracted reviews to disk, so that the data is persisted even after the browser tab is closed.

#### Acceptance Criteria

1. WHEN a valid Payload is received, THE Server SHALL generate a CSV Export_File using the column order: `Name`, `Stars`, `Title`, `Date`, `Description`, `Verified Purchase`, `Helpful Votes`.
2. WHEN a valid Payload is received, THE Server SHALL generate a JSON Export_File containing the full Payload including the `metadata` object and `reviews` array.
3. THE Server SHALL save Export_Files to a configurable output directory (defaulting to `./exports`).
4. WHEN `metadata.productTitle` is present, THE Server SHALL sanitize it by replacing all characters that are not alphanumeric, hyphens, or underscores with underscores, and truncating to a maximum of 60 characters.
5. WHEN both `metadata.productTitle` and `metadata.asin` are present, THE Server SHALL name each Export_File using the pattern `{sanitized_product_title}_{ASIN}_{YYYY-MM-DD}.{ext}`.
6. IF `metadata.productTitle` or `metadata.asin` is absent or empty, THEN THE Server SHALL name each Export_File using the pattern `reviews_{unix_timestamp_ms}.{ext}`.
7. IF the output directory does not exist, THEN THE Server SHALL create it (recursively) before writing Export_Files.
8. IF writing an Export_File fails for any reason (permissions error, disk full, directory creation failure, or other I/O error), THEN THE Server SHALL return HTTP 500 with a JSON body containing an `error` field with a descriptive message.

### Requirement 3: Serve Files for Download

**User Story:** As a user, I want to download the saved review files from the backend, so that I can access the exported data without the browser generating it each time.

#### Acceptance Criteria

1. WHEN a GET request is received at `/api/reviews/:fileId`, THE Server SHALL respond with the JSON Export_File for that `fileId` as a file download, setting `Content-Disposition: attachment; filename="{filename}.json"` and `Content-Type: application/json`.
2. WHEN a GET request is received at `/api/reviews/:fileId/json`, THE Server SHALL serve the JSON Export_File for that `fileId` as a file download, setting `Content-Disposition: attachment; filename="{filename}.json"` and `Content-Type: application/json`.
3. WHEN a GET request is received at `/api/reviews/:fileId/csv`, THE Server SHALL serve the CSV Export_File for that `fileId` as a file download, setting `Content-Disposition: attachment; filename="{filename}.csv"` and `Content-Type: text/csv`.
4. WHEN a `fileId` references a file that does not exist on disk, THE Server SHALL return HTTP 404 with a JSON body containing an `error` field with a descriptive message.
5. WHEN a GET request is received at `/api/reviews/:fileId/json` or `/api/reviews/:fileId/csv` and the specific format file does not exist for that `fileId`, THE Server SHALL return HTTP 404 with a JSON body containing an `error` field indicating the requested format is unavailable.

### Requirement 4: Health and Configuration

**User Story:** As a developer, I want a health check endpoint and configurable settings, so that I can verify the server is running and adapt it to different environments.

#### Acceptance Criteria

1. WHEN a GET request is received at `/health`, THE Server SHALL respond with HTTP 200 and a JSON body containing `{ "status": "ok" }`.
2. THE Server SHALL read the listening port from the `PORT` environment variable, defaulting to `3000` when the variable is absent or not a valid integer.
3. THE Server SHALL read the exports directory path from the `EXPORTS_DIR` environment variable, defaulting to `./exports` when the variable is absent or empty.
4. WHEN the Server process starts, THE Server SHALL log a startup message to stdout containing the listening port and the resolved exports directory path before accepting connections.

### Requirement 5: Chrome Extension Integration

**User Story:** As a developer, I want the Chrome extension to optionally send review data to the backend after extraction, so that users can choose between client-side CSV download and server-side storage.

#### Acceptance Criteria

1. THE Client SHALL read the backend URL from a user-configurable input field in the extension popup, persisting the value in `chrome.storage.local` under the key `backendUrl`.
2. WHEN extraction is complete and `backendUrl` is set to a non-empty string in `chrome.storage.local`, THE Client SHALL POST the extracted reviews and metadata to `{backendUrl}/api/reviews` with a request timeout of 30 seconds.
3. WHEN the POST request completes with a 2xx HTTP status, THE Client SHALL display a download link constructed as `{backendUrl}/api/reviews/{fileId}/csv` alongside the existing client-side CSV export button.
4. IF the POST request fails due to a network error, a non-2xx HTTP response, or a timeout, THE Client SHALL display an error message in the popup and SHALL still render the existing client-side CSV download button in a usable state.
5. WHEN `backendUrl` is absent, empty, or not set in `chrome.storage.local`, THE Client SHALL not attempt any POST request and SHALL render the popup UI identically to the pre-integration behavior.
6. THE Server SHALL include an `Access-Control-Allow-Origin` header permitting `chrome-extension://*` origins in all responses to requests from that origin.
